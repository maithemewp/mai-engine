## Security finding

`mai_get_dom_html()` decodes HTML entities across the whole serialized document, turning
escaped text back into live markup. Reproduced end to end on `sportsdataio` (WordPress
7.0.2), served over HTTP:

1. A Contributor types `<script>alert(1)</script>` as text in a paragraph block. The editor
   stores it escaped as `&lt;script&gt;...`.
2. `wp_kses_post()` leaves it untouched. Verified: escaped text survives sanitization,
   because escaped text is harmless text.
3. Contributors do not hold `unfiltered_html`. Verified: `false`.
4. The paragraph sits in a group block with a background color. Core block, core feature,
   no special capability.
5. `lib/blocks/group.php:39` passes its gate (`contentAlign || backgroundColor ||
   customBackgroundColor`) and runs the DOM round trip.
6. `mai_get_dom_html()` decodes the entities into live markup.

The served page contains `<script>alert(1)</script>`.

A control isolates the cause. Identical content with only the group background removed, so
the filter bails at its gate:

```
with group bg:     ESCAPED: <script>alert(1)</script>
without group bg:  ESCAPED: &lt;script&gt;alert(1)&lt;/script&gt;
```

Scope note, stated honestly: this needs an authenticated account that can create content,
and Contributor posts require review before publishing, though a reviewer sees the harmless
escaped form in the editor. It is not reachable by an anonymous visitor.

## Summary

Add a second PHPUnit suite that boots real WordPress via `wp-phpunit`, alongside the existing WordPress-free brain/monkey suite, without ever putting a with-dev Composer autoloader into the committed `vendor/`. Test dependencies move into a separate `tests/composer.json` installing to `tests/vendor/`, so the plugin's committed autoloader is never regenerated by a test run. Two regression tests seed the suites: one for `mai_render_block_handle_link_color()` needing real `WP_HTML_Tag_Processor`, and one characterization fixture for `mai_get_dom_document()` / `mai_get_dom_html()` that unblocks the long-deferred `HTML-ENTITIES` migration.

## Goals

1. Run tests against real WordPress core classes and APIs, and scale to future tests needing `WP_Query`, options and posts.
2. Make "the committed `vendor/` never contains a dev autoloader" a structural property rather than a discipline, so no CI configuration can violate it.
3. Keep the existing WordPress-free unit suite running exactly as it does today.
4. Keep every `npm run` script working unchanged.
5. Produce a fixture that makes the `mb_convert_encoding( ..., 'HTML-ENTITIES' )` migration a measured comparison rather than a third guess.

## Non-goals

- Full plugin activation under test. `lib/init.php` expects Genesis as the parent theme, and Genesis is not in the repo and is not Composer-installable.
- Fixing the behavior defects this work uncovered. They are recorded in "Findings" below with recommended follow-ups.
- Fixing the retired `_legacy/*` plugins, which carry the same decode. Out of scope by decision.
- Moving the linting dev dependencies out of the root `require-dev`. See "Out of scope".

Measured against `develop` at `bf24d2911`, not assumed.

- `composer.json` carries stale integration wiring: a `test-integration` script pointing at `tests/phpunit/integration/phpunit.xml.dist`, and an `autoload-dev` PSR-4 map `Tests\Integration\ => tests/php/integration/`. Neither path exists and the two disagree.
- `.github/workflows/deployable.yml` is the only workflow. No tests run in CI today.

- Local environment: PHP 8.4.23, Homebrew MySQL running, Docker installed but daemon not running, Node 20.

Facts that shaped specific decisions:

1. `lib/functions/utilities.php` has exactly one top-level statement (`defined( 'ABSPATH' ) || die;`) and no load-time hook registrations. `mai_get_dom_document()` and `mai_get_dom_html()` call zero WordPress APIs.
2. `lib/blocks/general.php` also loads bare. Its only genuine WordPress dependency is `WP_HTML_Tag_Processor`.
3. On PHP 8.4.23 the `HTML-ENTITIES` deprecation fires only on the encode direction. The decode direction that `mai_get_dom_html()` uses is silent. The encoding is still dropped in PHP 9.0.
4. `wp-phpunit`'s bootstrap requires `yoast/phpunit-polyfills`, ships `data/themedir1`, and defines `WP_DEFAULT_THEME` as `default`, so a content-free WordPress core boots.
5. `WP_UnitTestCase` cannot run on PHPUnit 10. See "Harness decision".

## Harness decision

**Chosen: `wp-phpunit` on host PHP against a local MySQL.**

It is already a dev dependency. It runs on the host PHP with no container, boots in under a second, and gives real WordPress including `WP_Query`, options, posts and the test factories, so it scales to the tests this suite exists to make possible.

**Rejected: `wp-env` (Docker).** The Docker daemon is not running on the development machine, it adds a Node dev dependency to an already large toolchain, start-up is materially slower, and Composer still runs inside the container so none of the dependency isolation problems go away.

**Rejected: a hand-rolled "load only `wp-includes/html-api`" harness.** It would be the fastest option and need nothing in CI, but it does not scale past the first test. This was verified concretely: loading `WP_HTML_Tag_Processor` standalone from a WordPress 6.9 tree required stubbing `wp_has_noncharacters()` and `wp_kses_uri_attributes()`, both of which live outside the html-api directory and neither of which was needed by older versions. That dependency surface grows with every WordPress release, so the harness rots by design.

### PHPUnit version constraint

`WP_UnitTestCase_Base::set_up()` unconditionally calls `expectDeprecated()`, which calls `PHPUnit\Util\Test::parseTestMethodAnnotations()` and `TestCase::getName()`. Both were removed in PHPUnit 10, so every test extending `WP_UnitTestCase` errors before its first assertion. This is not fixed by newer WordPress; `wp-phpunit` 7.0.2 carries the identical code, because WordPress core has not adopted PHPUnit 10.

Three options were evaluated and all three were run green:

- Pin PHPUnit `^9.6` for both suites. Rejected: the root `phpunit.xml.dist` then fails validation (`beStrictAboutCoverageMetadata` and the `<source>` element are PHPUnit 10 only), which violates goal 3, and `failOnDeprecation` would not exist for the encoding migration.
- Extend plain `PHPUnit\Framework\TestCase` after booting WordPress. Sufficient for the link-color test, but gives up factories and per-test transaction rollback, so it defeats the reason for choosing this harness.
- **Chosen:** keep PHPUnit `^10.5` everywhere and add a base class overriding `expectDeprecated()` to re-register the hooks without annotation parsing.

The chosen option was verified to preserve the post factory, per-test DB rollback isolation, `utf8mb4` round-tripping of emoji and Polish diacritics through MySQL, and the safety net that fails a test on an unexpected `_doing_it_wrong()`. The only loss is `@expectedDeprecated` / `@expectedIncorrectUsage` docblock annotations, which PHPUnit 10 does not read anyway; the `setExpected*()` method forms still work.

## Architecture

Two independent PHPUnit configurations with separate bootstraps.

- Root `phpunit.xml.dist` keeps the `unit` suite, which continues to run with no WordPress.
- New `tests/phpunit/integration/phpunit.xml.dist` for the WordPress suite, at the path the existing `test-integration` script already expects.

The WordPress suite boots WordPress but does not activate mai-engine. A loader on `muplugins_loaded` requires the plugin's committed runtime autoloader plus a curated list of `lib/` files. Verified: the hook fires with the plugin inactive, and it is early enough that the top-level `add_filter` calls in `lib/blocks/general.php` land before `render_block` is ever applied.

This is honestly "WordPress-loaded tests", not full-plugin integration. The spec uses the `integration` directory name for continuity with the existing script, but the limitation is real and is documented in the suite's bootstrap.

Note that `plugin-loader.php` boots two non-inert files inside a live WordPress: `plugin-update-checker/load-v5p7.php` registers an autoloader and factory versions, and `mai-cache/init.php` defines `Mai_Cache_Bootstrap` and registers an autoloader. Both come from the committed `vendor/`, so the integration suite has a hard dependency on the committed autoloader being valid.

## Dependency isolation

`tests/composer.json` holds the test dependencies and installs to `tests/vendor/`.

```json
{
  "name": "maithemewp/mai-engine-tests",
  "description": "Test-only dependencies for mai-engine. Installed into tests/vendor/ so the plugin's committed vendor/ autoloader is never regenerated with dev entries.",
  "license": "gpl-2.0-or-later",
  "require": {
    "php": "^8.1",
    "phpunit/phpunit": "^10.5",
    "brain/monkey": "^2.6",
    "wp-phpunit/wp-phpunit": "^7.0",
    "yoast/phpunit-polyfills": "^2.0",
    "roots/wordpress-no-content": "^7.0"
  },
  "autoload": {
    "psr-4": {
      "BizBudding\\MaiEngine\\Tests\\": "",
      "BizBudding\\MaiEngine\\Tests\\Unit\\": "phpunit/unit/",
      "BizBudding\\MaiEngine\\Tests\\Integration\\": "phpunit/integration/"
    }
  },
  "minimum-stability": "stable"
}
```

The pin is `^7.0` rather than the `^6.9` that the current `require-dev` happens to resolve, because the fleet has already moved. Sampled local site copies: `allhiphop` 7.0.2, `balloon-juice` 7.0.1, `eurweb` 7.0, `tvnewscheck` 6.9.5. Testing below the production floor means a WordPress behavior change that breaks a site can still pass CI, which matters here because `WP_HTML_Tag_Processor` is actively developed and the link-color test depends on it directly.

`wp-phpunit` and `roots/wordpress-no-content` are meant to track together; a comment in the file says so. Matching majors is sufficient. This was tested rather than assumed: wp-phpunit 6.9.4 against core 6.9.5 passes, and wp-phpunit 6.9.5 against core 7.0.2 also passes. There is no version assertion in the bootstrap, so real drift fails loudly as a fatal rather than silently, and the committed `tests/composer.lock` means it only moves on a deliberate `composer update -d tests`.

There is deliberately no `extra.wordpress-install-dir` and no `allow-plugins` block. `roots/wordpress-no-content` declares no dependency on `roots/wordpress-core-installer`, so with no plugin registered for type `wordpress-core`, Composer ignores `wordpress-install-dir` entirely and installs to `vendor/roots/wordpress-no-content/`. Rather than adding a Composer plugin to relocate it, `ABSPATH` points at where Composer actually puts it. One less moving part, and immune to this failure mode.

Root `composer.json` changes:

- Remove `phpunit/phpunit`, `brain/monkey` and `wp-phpunit/wp-phpunit` from `require-dev`, using `composer remove --dev phpunit/phpunit brain/monkey wp-phpunit/wp-phpunit` rather than hand-editing. Hand-editing is a no-op in practice: `composer.lock` is gitignored but present on every machine, and `composer install` installs from the lock, so the packages would persist in root `vendor/` indefinitely. This step needs the ACF Pro credential from `auth.json`, so it happens once, locally.
- Delete the `autoload-dev` block. Verified safe: `composer dump-autoload --no-dev --optimize` produces a byte-identical `vendor/composer/` tree with and without it, because `--no-dev` already ignores `autoload-dev`.
- `test-unit` becomes `tests/vendor/bin/phpunit --testsuite unit --color=always`, dropping both `composer dump` and the `auto_prepend_file` hack.
- `test-integration` becomes `tests/vendor/bin/phpunit --configuration tests/phpunit/integration/phpunit.xml.dist --color=always`.
- Add `test` running both, and `test-setup` running `composer install -d tests`.

`test-setup` is not hung off `post-install-cmd`. Doing so would make `npm run dev` download roughly 98 MB of WordPress core for every developer, including those who never run tests.

### Why this satisfies the no-dev-autoloader constraint

Today, `composer test-unit` runs `composer dump` with dev deps as its first action. That leaves the repository in a state where `deployable-guard` reports 16 missing paths (the Symfony polyfills and React promise pulled in by php-cs-fixer, plus Mockery, deep-copy, brain/monkey, phpunit and wp-phpunit). In other words, running the tests currently puts the repo into a guard-failing state, and only the pre-commit hook stands between that and a broken deploy.

After this change, running either suite never touches root `vendor/` at all. This was verified on a pristine checkout: after `composer install -d tests`, root `vendor/` has the identical 7,852 files, and the md5s of `autoload.php`, `autoload_files.php`, `autoload_psr4.php`, `autoload_static.php` and `installed.json` are unchanged, with root `composer.lock` untouched.

The residual exposure is the linting tools, which stay in root `require-dev`. See "Out of scope".

### .gitignore

Two additions, both load-bearing.

```
tests/vendor/
!tests/composer.lock
```

`!tests/composer.lock` must come after the existing `*.lock` on line 8. Verified with `git check-ignore --no-index -v`: with the negation after `*.lock` the file is tracked; with it before, `*.lock` wins and the lock is silently never committed, which would leave CI resolving unpinned on every run.

`tests/vendor/` is not optional and is not covered by the existing `vendor/*` rule, which is anchored to the `.gitignore`'s own directory and matches root `vendor/` only. `npm run beta` runs `git add -A && git commit && git push origin develop`, then merges and pushes `beta`. Both branches deploy as raw git trees to live sites. Without this line, `beta` pushes roughly 98 MB and 3,006 PHP files of WordPress core and PHPUnit to two deploy branches. Neither existing guard catches it: the pre-commit hook only fires when `vendor/composer/` is staged, and `DeployableChecker` reads only root `vendor/composer/autoload_files.php`.

Both `.gitignore` lines land in the same commit that adds `tests/composer.json`.

### Deleting define-abspath.php

`tests/phpunit/define-abspath.php` exists because PHPUnit's Composer bin proxy requires the root `vendor/autoload.php` before reading any bootstrap, and that eagerly loads `mai-cache/init.php`, which exits on an undefined `ABSPATH`. With `tests/vendor/bin/phpunit`, the proxy resolves its autoloader to `tests/vendor/autoload.php` and never reaches root vendor, so the file becomes dead.

Note that `tests/vendor/autoload.php` does have a files-autoloader, with 7 entries (deep-copy, two Mockery files, PHPUnit's assertion functions, brain/monkey's api.php, wp-phpunit's `__loaded.php`, and the polyfills autoloader). None of them is an `ABSPATH`-guarded WordPress drop-in, which is the actual reason this is safe.

The invariant that survives is subtle and its failure mode is silent: `tests/phpunit/unit/bootstrap.php` defines `ABSPATH` on line 5 *before* requiring the root autoloader on line 7. If those lines are ever reordered, or if a future `tests/composer.json` dependency adds an `ABSPATH`-guarded files-autoload entry, the process exits with status 0 and no output at all. The explanatory comment currently carried by `define-abspath.php` moves into `tests/phpunit/unit/bootstrap.php` above line 5 rather than being deleted with the file.

### wp-tests-config.php

Defines `ABSPATH` as `tests/vendor/roots/wordpress-no-content/`. Verified that the WordPress test bootstrap never defines `ABSPATH` itself, only reads it, so there is no conflict.

Database settings read `WP_TESTS_DB_NAME`, `WP_TESTS_DB_USER`, `WP_TESTS_DB_PASS` and `WP_TESTS_DB_HOST` from the environment, defaulting to `mai_engine_tests` / `root` / empty / `127.0.0.1`, which matches the running Homebrew MySQL. `DB_CHARSET` is `utf8mb4`, which matters for the emoji content this plugin handles. `$table_prefix` is `wptests_` as a plain local variable, which the wp-phpunit shim depends on.

The four constants the bootstrap hard-checks (`WP_TESTS_DOMAIN`, `WP_TESTS_EMAIL`, `WP_TESTS_TITLE`, `WP_PHP_BINARY`) are all set. `WP_TESTS_DIR` and `DIR_TESTDATA` are set by the bootstrap itself, and `WP_RUN_CORE_TESTS` is deliberately left undefined.

## CI

New `.github/workflows/tests.yml`. `deployable.yml` is not modified.

- Job `unit`: matrix PHP 8.1 and 8.4. `composer install -d tests`, run the unit suite. Every package in the generated lock accepts PHP 8.1 or looser, so the matrix resolves.
- Job `wp`: PHP 8.4, MySQL 8 service container. The official image refuses to start without `MYSQL_ROOT_PASSWORD` or `MYSQL_ALLOW_EMPTY_PASSWORD`, so the service sets a root password and the job passes it through `WP_TESTS_DB_PASS`. Health check on `mysqladmin ping` before the suite runs.

Neither job runs a root `composer install`, so no ACF Pro credential is needed anywhere in CI. A pristine `actions/checkout` tree plus `composer install -d tests` is sufficient, verified end to end.

Two assertions close the jobs:

- `git ls-files tests/vendor | wc -l` must be 0. This is the one that catches something real, namely the `.gitignore` regression described above.
- `git diff --exit-code -- vendor/`. This is a tripwire proving the test job did not dirty the committed autoloader, not proof that the committed autoloader is deployable. It structurally cannot catch a developer committing a dev autoloader, because CI diffs the working tree against that same bad commit. `deployable.yml` is what catches that, and it remains the real guard.

Because GitHub Actions gives each job its own checkout, the deployable job cannot observe anything a test job did.

## Test 1: RenderBlockLinkColorTest

Covers `mai_render_block_handle_link_color()` in `lib/blocks/general.php`, which has two known shipped regressions:

- **BUG1**, the guard. Introduced in `366b63788`, fixed in `d2a559cb2`. A `str_contains( $block_content, 'has-link-color' )` guard early-returns on background and overlay blocks, because `has-link-background-color` does not contain `has-link-color`.
- **BUG2**, the lost text rewrite. Present since `d23afd367`, fixed in `89250280f`. The background pass rebuilt the processor from a `$block_content` that had not absorbed the text pass, and the return came from that processor.

Four historical versions of the function were reconstructed and every candidate case was run against all of them. An earlier draft of this spec proposed seven cases; three were vacuous (passing against every buggy version) and one was a byte-identical duplicate. The list below is what actually locks behavior.

### Assertion mechanism

`WP_HTML_Tag_Processor::has_class()` exists as of WordPress 6.4 and is the right tool, but the earlier justification for it was wrong. The implementation's `explode` / `array_flip` / `implode` round-trip is fully deterministic: the removed class's slot collapses and the new class is appended last. There is no reordering to defend against. The real reasons to avoid raw string equality, both measured, are that `set_attribute()` normalizes attribute quoting (`class='a'` becomes `class="a"`) and re-encodes entities in the value (`a&b` becomes `a&amp;b`), while leaving the rest of the tag untouched.

Three hazards the tests must handle:

- `has_class()` returns `?bool` and returns `null` when the processor is not positioned on a tag, so `assertFalse( $p->has_class( ... ) )` passes identically whether the class is absent or the tag was never found. Tests assert the `next_tag()` return value first.
- `has_class()` is scoped to one tag. The assertion that actually catches BUG2 is the document-wide negative "no tag anywhere still carries `has-link-color`", which requires an explicit `while ( $p->next_tag() )` walk. A helper on the base class provides it.
- Element positioning differs per fixture. In a group block both classes sit on one element; in a cover block the text class is on the wrapper and the background class is on the `wp-block-cover__background` span. Tests navigate deliberately rather than matching on `has-links-color`, which would be circular since that is the implementation's own matcher.

Two further notes. `has_class()`'s docblock claims ASCII case-insensitivity, but the body gates that on quirks mode; in the default mode it is case sensitive. This is consistent with the `str_contains` guard, so there is no behavioral gap, but the docblock should not be trusted.

And the trailing-hyphen refinement in the guard (`has-link-` rather than `has-link`) is not observable through this function's output: the inner `next_tag()` matchers use full class names, so the shorter guard produces byte-identical results. It is a performance-only refinement and cannot be unit tested here. That is worth stating explicitly in the test file, because that guard is exactly where BUG1 came from.

Finally, calling the filter with `$block['attrs']` absent emits three `Undefined array key` warnings on every version including current. Under `failOnWarning` that is a test failure. Tests always pass an `attrs` key; guarding the function with `$block['attrs'] ?? []` is a recommended follow-up, since `render_block` is a public filter that third parties apply.

## Test 2: DomEncodingTest

A characterization fixture at `tests/phpunit/unit/fixtures/encoding.php`, one row per input, each recording the exact current output of `mai_get_dom_html( mai_get_dom_document( $in ) )`. It lives in the WordPress-free unit suite because neither function touches WordPress, so it runs in well under a second with no database and no WordPress, which is what makes iterating the migration against it practical.

### Golden storage

Goldens are stored as escaped or hex-encoded literals, never as raw UTF-8 in a PHP array, and the trailing newline that `saveHTML()` appends to every output is recorded explicitly. This is not theoretical fastidiousness: the draft of this spec recorded a golden as `... 🎉  x` with two spaces when the real output has U+0020 followed by U+00A0, lost to a copy/paste round trip. That is precisely the failure mode the fixture exists to prevent.

### Case groups

**G1, baseline (17 rows).** Polish diacritics, curly quotes and apostrophes, em and en dashes, pre-escaped `&amp;` `&lt;` `&gt;` `&quot;` `&#039;` `&nbsp;`, double-escaped `&amp;amp;`, bare ampersand, ampersand in an `href`, BMP emoji, astral emoji, ZWJ sequence, existing numeric entity, nested markup, and a combined string.

**G2, Unicode noncharacters and the numeric boundary.** `&#0;`, `&#55296;` (surrogate), `&#64976;` (U+FDD0), `&#65533;`, `&#65534;`, `&#65535;`, `&#1114109;`, `&#1114110;`, `&#1114111;`, `&#1114112;` (out of range).

This group is not optional. It is the **entire** divergence surface between the current implementation and candidate A, the leading replacement. Without it the fixture produces zero signal for that comparison and a migration would be adopted by luck rather than by coverage. G1 alone matches on every row for both implementations.

**G3, escaping-sensitive rows, pinned deliberately.** `&lt;script&gt;alert(1)&lt;/script&gt;`, `&lt;img src=x onerror=...&gt;`, `&quot;` and `&#039;` inside attribute values, `&amp;amp;`, entity-bearing `<script>` and `<style>` bodies, `<textarea>` and `<pre>` content. These record dangerous current behavior; see "Findings".

**G4, malformed and structural.** Unclosed tags, crossed tags, stray `<` and `>` in text, comments containing entities, CDATA (libxml rewrites it into a comment regardless of decode choice), and empty string, which returns `"\n"` rather than `""`.

**G5, international.** RTL text with bidi control characters, CJK, precomposed NFC versus NFD combining sequences, Vietnamese stacked diacritics, raw U+00A0, soft hyphen U+00AD.

**G6, inline SVG.** Included because `lib/functions/icons.php` is a caller and HTML named entities are invalid in XML and SVG.

**G7, quotes and JSON in data attributes.** Straight and curly quotes in one string, Polish in both cases, typographic characters, and five shapes of `data-*` attribute carrying JSON: single-quoted, pre-escaped, mixed with other attributes, alongside an entity-bearing `href`, and a combined case. Every `g7_data_*` row currently records corrupted output. This group pins F5.

Twelve pathological inputs were also checked for a crash in the `getElementsByTagName('div')->item(0)` dereference, including a bare `</div>`, a lone doctype, 300-deep nesting and an embedded null byte. libxml always synthesizes the wrapper, so no crash path was found. No fixture row is needed for this.

## Encoding migration: pulled forward, fix-first

Originally deferred to its own spec. The security finding above changed that: this is a
live vulnerability, not a deprecation cleanup, so the fix leads and the test-suite
infrastructure follows.

The fixture still lands first. Two prior attempts at this migration were reverted after
Polish diacritics and other non-English content broke, and the surviving code comment
blames the wrong change for it (see "Correcting the record"). Shipping a third attempt with
no regression net would repeat that history.

What has *not* changed is the deprecation timeline, and it was never the driver. Measured on
PHP 8.4.23 the remaining call is the decode direction, which emits no deprecation at all;
only the encode direction does, and that side already migrated to `mb_encode_numericentity`
in `28310b4df`. PHP 9.0 dropping the encoding is a distant deadline. The reason to move now
is the XSS, nothing else.

### Verification cannot rest on synthetic fixtures alone

The fixture rows were authored by me, so they only cover failure modes I anticipated, which
is precisely the gap that sank the previous attempts. Before the fix is applied, every post
in the local Herd sites gets run through both the current and candidate implementations and
diffed, with each changed post reviewed by hand. That is a corpus of real editorial content
rather than a guess at what might break, and it is the only step that can catch a content
class nobody thought to write a fixture for.

### Correcting the record

The in-repo comment at `lib/functions/utilities.php:1417-1425` attributes the commits correctly but its conclusion, that both alternatives broke non-English content, is an inference the diffs do not support.

| Commit | Date | Encode side | Decode side |
|---|---|---|---|
| `243d3398a` | 2024-01-18 | `mb_encode_numericentity` | `mb_convert_encoding` |
| `0b425cb87` | 2024-06-28 | `mai_convert_quotes()` plus `mb_encode_numericentity` | `html_entity_decode( ENT_QUOTES \| ENT_HTML5 )` |
| `e5e8ff818` | 2024-07-10 | removed entirely | removed entirely |
| `8c51375c9` | 2025-01-08 | `mb_encode_numericentity` restored | `mb_convert_encoding` restored |

`0b425cb87` already used `ENT_QUOTES | ENT_HTML5`. It also introduced a `wptexturize`-based change on the encode side, so the decode swap was never observed in isolation, and `wptexturize` is by far the likelier cause of anything quote-shaped. What `8c51375c9` recovered from was `e5e8ff818` removing the **encode** step, which is the classic libxml-reads-UTF-8-as-Latin-1 mojibake and is unrelated to the decode function. There is no evidence in git that `html_entity_decode` alone ever broke anything.

### Measured comparison

Five implementations were run over 65 fixtures covering all six groups above.

| Implementation | Rows differing from current |
|---|---|
| A: `html_entity_decode( $h, ENT_QUOTES \| ENT_HTML5, 'UTF-8' )` | **1 / 65** |
| B: `mb_decode_numericentity( $h, [0x80, 0x10FFFF, 0, 0x10FFFF] )` | 32 / 65 |
| B': same with an exact-inverse mask | 32 / 65, identical to B on every row |
| No decode at all (what `e5e8ff818` shipped) | 55 / 65 |
| C: no encode, no decode, UTF-8 declared to libxml | 14 / 65 |

**Candidate B is a non-starter.** `saveHTML()` emits HTML 4 *named* entities for everything in that set and numeric references only for the rest, so `mb_decode_numericentity` leaves every Latin-1 accent, curly quote, dash, `&nbsp;`, `&shy;`, `&zwj;` and bidi mark encoded. It changes the output of all 18 call sites, and named entities are invalid in XML and SVG while `icons.php` is a caller. The mask choice is irrelevant.

**Candidate A diverges only on Unicode noncharacters.** PHP's `html_entity_decode` refuses to decode numeric references to noncharacters, where mbstring decodes them to raw bytes. Since noncharacters are illegal in interchange, A's behavior is defensible and arguably better. Nothing else moves across 65 rows.

### Handover to the encoding spec

The measurements above are the starting point, not a decision. The encoding spec owns the choice between candidates A and C, the F3 escaping question they interact with, whether the G2 noncharacter rows are an acceptable behavior change, and when `failOnDeprecation` gets enabled.

Its two hard prerequisites are phase B, the fixture existing with every golden reviewed by hand, and phase C's corpus diff over real content. Neither is skippable: the fixture covers only anticipated failure modes, and the corpus is what covers the rest.

### Candidate C, now the leading option

Drop the `mb_encode_numericentity` encode as well, declare UTF-8 to libxml, and do no decode at all:

```php
$dom->loadHTML( '<?xml encoding="UTF-8">' . "<div>$html</div>", LIBXML_HTML_NOIMPLIED | LIBXML_HTML_NODEFDTD );
// and mai_get_dom_html() becomes just: return $dom->saveHTML();
```

It differs from current on 14 of 65 baseline rows, and every one of those is current losing escaping. Measured directly on the content classes that matter here:

| Input | Candidate C output |
|---|---|
| `<div data-config='{"title":"Zażółć & B","n":1}'>` | correctly escaped, JSON intact |
| `ZAŻÓŁĆ gęślą jaźń ąćęłńóśźż` | unchanged raw UTF-8 |
| `"straight" 'single' “curly” ‘s’ it’s` | unchanged raw UTF-8 |
| `🎉 👩‍💻 ☕` | unchanged raw UTF-8 |
| `&amp; &lt; &amp;amp;` | escaping preserved |
| `&lt;script&gt;alert(1)&lt;/script&gt;` | stays escaped |
| `© ™ € — … →` | unchanged raw UTF-8 |

So C resolves F3 and F5, keeps every non-English and typographic case identical to today, and uses no deprecated API on either side. Its one behavior change is that pre-escaped entities stay escaped instead of being decoded, which is correct HTML rather than a regression.

It is a larger change than this work scopes and has not been stress-tested against all 18 call sites, which is why it belongs to the encoding spec rather than here. But it should enter that spec as the leading option, not as an afterthought.

Note on the longer-term direction: `~/LocalPackages/mai-dom` is the eventual replacement for these helpers. It depends on PHP 8.4's `Dom\HTMLDocument`, a real HTML5 parser, which is not a realistic floor for a premium theme and plugin today. Candidate C works on the current `^8.1` floor and captures most of the correctness win in the meantime, so it is the right interim step rather than a competing direction.

## Findings: defects discovered, not fixed here

All four were reproduced against current `develop`. None is fixed by this work. Each is pinned by a characterization test so that fixing it later is a visible, deliberate diff.

**F1. Only the first match is rewritten.** The `break` in each of the three passes in `mai_render_block_handle_link_color()` means a second matching element is never converted.

```
in : <p><mark class="has-link-color">one</mark> and <mark class="has-link-color">two</mark></p>
out: <p><mark class="has-links-color">one</mark> and <mark class="has-link-color">two</mark></p>
```

Two highlights in one paragraph is ordinary content, and the commit that introduced this path was titled "Fix inline highlights when using link color". A surviving `has-link-color` is not cosmetic; under WordPress 6.4 and later that class means link element color, which is the exact collision this filter exists to prevent. The fix is not simply removing the `break`s: the existing comment explicitly notes that this filter runs for every block on every page and that an unmatched `next_tag()` walks the entire subtree, so removing the early exit has a real performance cost that needs its own measurement.

**F2. Class matching splits on the space character only.** `next_tag( ['class_name' => ...] )` and `has_class()` split on all ASCII whitespace; the implementation uses `explode( ' ', ... )`, so `unset()` misses and the output carries both classes.

```
in : <p class="has-text-color⇥has-link-color">Text</p>
out: <p class="has-text-color⇥has-link-color has-links-color">Text</p>
```

Low field likelihood since core joins with single spaces, but real. The round-trip is also not whitespace-lossless: `"  a b  "` collapses to `" a b"`.

**F3. `mai_get_dom_html()` blind-decodes entities across the whole document.** It un-escapes what DOMDocument deliberately escaped. Candidate A shares this behavior exactly; candidates B and C do not.

```
<p>&lt;script&gt;alert(1)&lt;/script&gt;</p>       →  <p><script>alert(1)</script></p>
<a title="a&quot; onmouseover=&quot;alert(1)">   →  <a title="a" onmouseover="alert(1)">
<script>if (a &amp;&amp; b &lt; c) x("&quot;");</script>  →  JS corrupted
<p>&amp;amp;</p>                                 →  <p>&amp;</p>
```

Escaped text becomes live markup, attribute values break out of their quotes and gain event handlers, and one level of escaping is lost per pass. Eighteen call sites round-trip user-authored content through this, including `lib/blocks/paragraph.php`, `heading.php`, `group.php`, `button.php`, `lib/functions/shortcodes.php` and `lib/support/woocommerce.php`.

This is recorded as G3 in the fixture, explicitly labelled as pinning known-dangerous behavior rather than endorsing it. Candidate C is the only evaluated option that resolves it, and choosing it is inseparable from choosing the replacement for `mb_convert_encoding`, which is why the two move together in phase C.

Reachability is no longer open. `wp_kses_post()` was traced and it leaves escaped text untouched, so a Contributor without `unfiltered_html` can reach this. See "Security finding" at the top; this is a confirmed vulnerability, not a defect of unknown severity.

F5 below is the same defect reaching a content shape that needs no attacker at all.

**F4. The unit suite is currently red.** Unrelated to this work but blocking, since CI cannot be added over a failing suite.

```
MaiQueryCacheInvalidationTest::test_pre_query_passes_through_when_not_cacheable
Error: Call to undefined function wp_using_ext_object_cache()
  lib/classes/class-mai-query-cache.php:282
```

`wp_using_ext_object_cache` is stubbed in `MaiQueryCacheSingleFlightTest.php:24` but not in the invalidation test. The fix is a `Functions\when()` stub matching the sibling tests, and it lands in this work because goal 3 requires the suite to be green before CI runs it.

**F5. JSON in a data attribute is corrupted into invalid HTML.** This is F3 reaching ordinary content rather than attacker-supplied content, and it needs no unusual input at all.

```
in : <div data-config='{"title":"Zażółć & B","n":1}'>x</div>
out: <div data-config="{"title":"Zażółć & B","n":1}">x</div>
```

The attribute terminates at the first `"` inside the JSON, so a browser parses `data-config="{"` followed by garbage attributes, and the payload is gone.

Attribution is unambiguous, measured at each stage:

| Stage | Output |
|---|---|
| `saveHTML()` alone | `data-config="{&quot;title&quot;:&quot;Za&#380;&oacute;&#322;&#263; &amp; B&quot;,&quot;n&quot;:1}"` |
| current | `data-config="{"title":"Zażółć & B","n":1}"` |
| candidate A | `data-config="{"title":"Zażółć & B","n":1}"` |
| candidate B | `data-config="{&quot;title&quot;:&quot;Zaż&oacute;łć &amp; B&quot;,&quot;n&quot;:1}"` |
| candidate C | `data-config="{&quot;title&quot;:&quot;Zażółć &amp; B&quot;,&quot;n&quot;:1}"` |

DOMDocument escapes the attribute correctly on its own. The decode step is what breaks it. Pre-escaped input is destroyed identically: `data-config="{&quot;a&quot;:1}"` comes back as `data-config="{"a":1}"`.

This changes the candidate assessment. Candidate A was leading purely on being byte-identical to current across 65 fixtures, but "byte-identical to current" now demonstrably includes "corrupts JSON data attributes into invalid HTML". A does not fix F5. C does, and C also keeps Polish diacritics, straight and curly quotes, emoji including ZWJ sequences, and typographic characters as raw UTF-8, exactly as today.

Pinned by fixture group G7.
